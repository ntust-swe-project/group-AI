# 系統層 Spec

各 feature 的共同前提。**不寫機制與數值**（`VISION.md` §11.2）—— 數值在 feature 檔裡定，或列為下面的待決項。

本檔的輸入只有兩份：`VISION.md` 與 `docs/meeting/001-客戶訪談.md`。每條都標出處，追不到的就是 `INV`。

## 1. 邊界

### 做哪些系統

| 系統 | 支撐什麼 | 出處 |
| --- | --- | --- |
| 時間推進 | 以「天」為單位推進到第 30 天 | §4.1 |
| 殖民者 | 個體的生理與心理狀態、工作執行 | §3.1、Q2 |
| 指派與優先度 | 間接控制：玩家下令、殖民者自己執行 | §3.2、Q5 |
| 建造與自動化 | 減輕管理負擔、應對危機 | §3.3 |
| 危機 | 逐波加壓，無預警。分外部／內部／人三類 | §3.4、§8、Q3 |
| 失敗判定 | 太空站毀損（必做）等條件觸發即結束 | §7 |
| 結算 | 呈現發展水準與存活天數，並說明輸的原因 | §4.4、Q6、Q7 |

### 系統之間怎麼牽動

危機消耗太空站與殖民者 → 殖民者狀態惡化會降低工作產出 → 產出不足使發展水準停滯 → 發展水準不足則自動化無法回本（Q4）→ 無法回本就擋不住下一波危機。**這條迴圈是壓力的來源，不是某個單一數值。**

另有一條獨立的因果鏈，跨兩個子系統：**心理惡化 → 失能 → 影響生理 → 死亡**（Q8）。它表示心理不是裝飾性指標。

**危機三類的「人」指什麼**：§8 在「人」底下只舉一個例子 —— 殖民者的生理與心理狀態惡化。所以「人」是**殖民者自身成為危機來源**（有人倒下、工作停擺、照顧他又佔用別人的工時），**不是殖民者之間的衝突**。殖民者之間是合作關係（§3.1），叛徒與敵對機制 §6 已列範圍外。上面那條因果鏈就是這一類危機的完整內容。

### 本組再收斂的「不做」

`VISION.md` §6 已列的範圍外不重複。以下是本組在 prototype 階段額外不做的：

- 多張地圖或地圖生成 —— §6 已限單一太空站地圖，本組進一步固定為單一預設佈局
- 視覺只到 wireframe —— §6 已把正式美術與音效列為範圍外，本組進一步不做任何美化
- 難度選項、教學關、設定選單
- 存檔與續玩（§6 已列範圍外，這裡重申，因為它會影響資料結構要不要可序列化）
- 殖民者之間的社交關係與衝突 —— §3.1 明定殖民者為合作關係，不做敵對或派系

## 2. 共用概念

命名是本組的設計產出，不是 VISION 的規定。**各 feature 一律沿用這裡的名字**，不另起別名。

| 概念 | 程式識別字 | 說明 | 出處 |
| --- | --- | --- | --- |
| 天 | `Day` | 推進的最小時間單位，危機波次掛在天數上。一天多長由 feature 定 | §4.1 |
| 太空站 | `Station` | 玩家經營的場所，具備完整度（毀損的反面） | §7 |
| 發展水準 | `DevelopmentLevel` | 太空站的發展程度。**被兩處引用**：自動化回本的門檻（Q4）與結算指標（Q7） | Q4、Q7 |
| 殖民者 | `Colonist` | 個體。數量**非固定**，初始 3–4 個，過程中可透過事件增加 | §3.1、Q1 |
| 生理狀態 | `Physiology` | 與心理**分開**呈現，不合併為單一指標。五條需求：`Hunger`（吃）、`Thirst`（喝）、`BodyTemp`（體溫）、`Relief`（排泄）、`Stamina`（體力） | Q2、組內 2026-11-10 |
| 心理狀態 | `Psychology` | 同上。兩條：`Stress`（壓力）、`Mood`（心情）。惡化會導致失能，進而影響生理 | Q2、Q8、組內 2026-11-10 |
| 失能 | `Incapacitated` | 殖民者暫時無法工作的狀態，是死亡的前置 | Q8 |
| 指派 | `Assignment` | 玩家下的命令，帶優先度 | §3.2、Q5 |
| 優先度 | `Priority` | 指派與當前工作都有。指派的優先度較高時**立即搶占**當前工作 | Q5、Q5 補充 |
| 設施 | `Facility` | 玩家建造的東西 | §3.3 |
| 自動化 | `Automation` | 先投入、後回本的設施能力 | §3.3、Q4 |
| 危機 | `Crisis` | 波次化的壓力來源，**不給預警**。三類見下方說明 | §3.4、§8、Q3 |
| 失敗條件 | `FailureCondition` | 觸發即結束。判定結果必須帶**哪一條被觸發**，不能只回傳成功或失敗 | §7、Q6 |
| 事件 | `Event` | 需要玩家決定的插入點，例如是否收編新殖民者 | Q1 |
| 結算 | `Summary` | 一場結束後的呈現：發展水準、存活天數、失敗原因 | §4.4、Q6、Q7 |

### 3.1 S4 的四種寫法

`VISION.md` §3 的張力原句是「自動化是先投入、後回本，一場只有 30 天，回本來不來得及發生？」——
所以「回本」要先有定義，「閾值」才有意義。

| | 「回本」的定義 | 「閾值」是什麼 | 驗收條件寫得出來嗎 | 代價 |
| --- | --- | --- | --- | --- |
| **A 絕對門檻** | 自動化設施開始淨產出（產出 > 維護成本） | `DevelopmentLevel ≥ X`，X 是固定值 | 容易：一條不等式，純邏輯可單測 | 與危機強度脫鉤。後期危機變強但門檻不動，玩家過了門檻就一路順 |
| **B 相對天數** | 同 A | 門檻隨天數上升：第 N 天要達到 `f(N)` | 容易：給定 N 與發展水準即可判定 | 等於把「每天都有壓力」寫成一條成長曲線，落後就吃苦。但曲線本身要調，而且玩家感受不到門檻存在 |
| **C 相對危機強度** | 自動化產出 ≥ 當前波次的消耗 | 門檻是「追得上危機」的那個發展水準 | 難：要先定義危機消耗量，耦合最深 | 最貼近體驗（回本＝擋得住），但危機與自動化綁死，任一邊改了另一邊要重測 |
| **D 投資回收期（採用）** | 單一設施的**累積淨產出 ≥ 建造成本** | 讓「回收期 < 剩餘天數」成立的那個發展水準 | 容易且直接：回收期是可算的天數，純邏輯可單測 | 要為每個設施記建造成本與累積產出，資料多一層 |

**2026-11-10 組內定案：採用 D。** 三個理由：① 它是「回本」的字面意思，不用再解釋；② 它直接回答 VISION 的張力 —— 「來不來得及」變成「回收期 vs 剩餘天數」的比較，可以量；③ 它讓落後懲罰自然出現：越晚蓋，剩餘天數越少，同一個設施就越不值得蓋，玩家不需要被告知門檻也感覺得到。

A 最省事但會讓後期沒有張力；C 最準但把危機與自動化綁成一個不可分割的 feature，違反我們「一輪做得完」的 task 切法。

D 與 SC9 是同一個設計取向的兩面：壓力放在「平時累積夠不夠」，不放在「臨場反應快不快」。
